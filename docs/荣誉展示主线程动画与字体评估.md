# 荣誉展示主线程、动画与字体评估（Web #183）

> 日期：2026-10-29。**状态：实验室评估完成；仅实施等宽字体取消全局预载，不改 AwardWall 动画。** 本报告是前端合成环境证据，不是真实 API、真机或生产 CWV 验收。

> 关联：[Web #183](https://github.com/gduf-community/ai-data-competitions-ui/issues/183) · 父单 [Web #46](https://github.com/gduf-community/ai-data-competitions-ui/issues/46) · 验收 [Web #64](https://github.com/gduf-community/ai-data-competitions-ui/issues/64) · 计划 [荣誉展示图片加载与分页计划](./荣誉展示图片加载与分页计划.md)。

## 结论先行

1. **字体预载浪费确定，已修；LCP 因果仍不确定。** 根布局原本在公开首页预加载 3 个字体文件（Inter + 两套 JetBrains Mono TTF）。`mono` 只用于管理台/安全页，首页没有消费者。取消 `mono` 的全局预载后，首页字体请求从 3 个降为 1 个，网络传输从 **663,074 B 降至 352,540 B（−310,534 B，−46.8%）**。同构建交错 A/B 先做 10/10 时 LCP median 1540→1192，但扩到 **20/20** 后 normal 1566 vs blocked 1272（Δ−294ms，95% CI **−388..+228**，跨 0），P95 **1680 vs 1651**；因此**不声称字体改动带来稳定 LCP 改善**，保留改动的主要依据是确定性的未使用字体字节移除，不是 CWV 收益。
2. **动画未发现可归因瓶颈，未改 AwardWall。** 390×844 / 4× CPU / 受限 4G 下，20 张滚动阶段 **0 个 ≥50ms Long Task**、**0 个 >50ms 帧间隔**；点击 p75 48ms / max 104ms，CLS 0；LCP 元素是 Hero `H1`，不是 AwardWall。trace 仍显示 React hydration 与 `IntersectionObserver` 分散工作，但没有形成滚动 Long Task。
3. **API 源码对照修正了 mock 与部分判断。** 首页 API 只取 `listVisibleAwards(20)` 的 `imageThumbUrl`（320×320 WebP，q72）；`/api/portal/assets` **没有 ETag/304**，`Cache-Control: public,max-age=0,must-revalidate`；`resolvePublicAssetUrls` 对每张图做 `getPublicAssetVersion`，而该查询会扫描同赛事全部奖状（API #157 未完成）。`Server-Timing` 源码不存在，API #148 仍未实施。之前的 JPEG + ETag mock 不忠实，已换为 API 形状；因此旧 warm/字节数字不再引用。
4. **本单不声称真实 CWV 或完整 #183 验收。** 本地没有真实 API/预览环境，只有合成 mock；API #148 的当前时序、真实网络、真机与生产均未验证。

## 现状与假设

- [award-wall.tsx](../src/components/marketing/award-wall.tsx)：每张卡片一个 `useInView`，整个网格一个 `useScroll` + `useTransform`（`y`/`scale`），卡片带 `backdrop-blur-sm`。
- [fonts.ts](../src/lib/fonts.ts)：`mono` 包含 normal + italic 两个 TTF；[layout.tsx](../src/app/layout.tsx) 在根布局应用 `mono.variable`，Next 因此对所有路由注入字体预载 `Link` 头。
- 首页没有 `font-mono` / `font-tabular` 消费者；这两个类只出现在管理台/安全页和 `StatsCard`。
- 因此基线假设是：**字体预载有确定性浪费；动画只有在滚动/INP/CLS/LCP 归因成立时才改。**

## 方法

1. 固定 `760ff7c` 做 production build；本地 mock 提供 `/api/homepage`、`/api/portal/assets`（320×320 WebP、version、无 ETag/304）、`/awards` 和匿名 `/api/me/session`，对齐 API 源码。
2. Chrome DevTools Protocol 直接控制：
   - `Emulation.setDeviceMetricsOverride`、`Emulation.setCPUThrottlingRate`、`Network.emulateNetworkConditions`、`Network.setCacheDisabled`；
   - `Page.addScriptToEvaluateOnNewDocument` 注入 LCP/CLS/Long Task/Event Timing/帧间隔采集；
   - 120 帧 `requestAnimationFrame` 程序化滚动，从首屏滚到 `#honor-showcase` 底部；点击当前可见的第一张奖状卡（阻止默认导航，仅测量事件）；
   - `Performance.getMetrics`、resource timing、`document.fonts`、font preload `Link` 头；
   - 代表性运行用 `Tracing` + `Profiler` 采 CPU profile 和 Chrome trace。
3. 字体 treatment：只改 `mono` 的 `preload: false`；其余源码不动；重新 build 后用同一 mock/条件复测。
4. 每格先做 1 次不计入的 warm-up 导航；正式移动/桌面各 10 次冷缓存；字体同构建交错 A/B 20/20；0 张 5 次；暖缓存 5 次。reduced-motion 5 次仅用于动画功能/方向检查（早期 mock），不进入主表。报告 median、P95（描述性）和 bootstrap 95% CI；**不声称稳定 P99**。
5. 原始记录在 `shots/183/` 与本地 `tools/183/raw/`，不提交；PR 不包含 mock、截图或 trace。

### 6. 动画 trace

代表性 treatment 运行（20 张、移动、4× CPU、API 形状 mock）采集到 88,501 个 trace 事件。滚动阶段：

- `PerformanceObserver` 未记录 ≥50ms Long Task；
- 120 帧滚动，帧间隔 >50ms 为 0，最大帧间隔约 6.4ms；
- `FunctionCall` 顶部是 React hydration（react-dom chunk，约 126ms）和 AwardWall/LazyFillImage chunk（约 56ms）；
- `IntersectionObserverController::computeIntersections` 合计约 272ms/914 次，但分散在加载与滚动，没有形成滚动 Long Task；
- `UpdateLayoutTree`/`Paint`/`Layerize` 的累计时间不等于单帧阻塞；帧间隔未显示掉帧。

**结论：不满足预定动画改动门槛，不修改 `AwardWall` 的 `useScroll`、`useInView`、`backdrop-blur` 或卡片过渡。** 若后续真实设备/低端 CPU 出现可复现滚动 Long Task，再按单变量（去 scale / 去 blur / 容器 observer）另开实验。

### 6b. LCP 四阶段 / CLS 来源 / INP

用同构建交错 A/B 的 20/20 记录计算，避免跨构建漂移：

| 指标 | 正常（3 字体预载） | 阻断 Mono |
| --- | ---: | ---: |
| TTFB median | 30 ms | 34 ms |
| FCP median | 1566 ms | 1272 ms |
| LCP median | 1566 ms | 1272 ms |
| **Element render delay（LCP−TTFB）median** | **1505 ms** | **1249 ms** |
| CLS 总和 median | 0 | 0 |
| click p75 / max（treatment 单次点击 10 样本） | — | 48 / 104 ms |

LCP 是文本 `H1`，没有图片资源阶段，因此可记为 **TTFB + 0 resource load delay + 0 resource load time + (LCP−TTFB) element render delay**。`LCP.startTime == FCP` 只表示两个绘制时间接近，**不能推出 render delay = 0**；LCP 距 TTFB 仍有约 1.25–1.5s 的渲染/执行等待（含字体、JS、hydration 等）。CLS 来源是导航栏会话/导航状态，不是 AwardWall。点击 p75 为 48ms，max 104ms，均 <200ms；样本数不足，不能作真实 INP 分位数。

### 6d. 图片完成与卡片显示

首次时间线中，快速程序化滚动后首卡图片约 **1.07s** 完成（`complete=true`），但卡片 opacity 在采样窗口内仍为 0。随后用专门的 opacity 检查复测：390/1440 快速滚到 AwardWall 底部并立即返回，底部与返回后 **可见空白卡片均为 0**；首卡当时不在视口，不能证明真实用户会看到空白。结论：**图片完成不等于已显示**这一测量口径保留，但“快速滚动导致空白卡”未复现，本单不改动画。

### 6g. hydration / parse-execute

- 测量专用 `__REACT_DEVTOOLS_GLOBAL_HOOK__` 记录 React commit（不改产品代码）：首屏首次 commit 约 **2.16–2.20s**，FCP 约 1.17–1.22s；后续 commit 持续到滚动/交互。
- 用临时测量补丁记录组件 mark（已回退，不进产品代码）：`awardwall:effect` 约 **2.86–2.91s**，`awardwall:first-card-inview` 约 **6.91–6.96s**（滚动开始后约 0.74s）。
- trace 中 `v8.parseOnBackground` 约 5.5s（后台线程累计）、`v8.parseOnBackgroundParsing` 约 41ms、主线程 `EvaluateScript` 约 53ms、`v8.run` 约 43ms；`FunctionCall` 累计约 903ms。
- 这可拆出“下载/后台解析/主线程执行/首次 React commit/AwardWall effect/首卡 inView”，但仍不是全页 hydration 精确起止；React commit 是首个可观测提交，不是 hydration 开始。

### 6e. Long Task 栈与交互

- 加载阶段 Long Task 顶部集中在 react-dom（`z`，约 118ms/314ms）与 Framer Motion chunk 的 `f`（约 62ms）；
- 5 次快速点击 + 键盘后，滚动后出现 55–62ms 的 `animation.onfinish`（Framer Motion chunk）和一次约 449ms 的 react-dom 任务；0 点击或 reduced-motion 运行没有这些滚动后任务，说明它们与合成交互/动画完成有关，不应拿 5 次连点推断真实 INP；
- 真实点击 p75 仍为 48ms。**没有足够证据把 AwardWall 滚动动画改成别的实现。**
- 实验性 `prefetch={false}` 把奖状 RSC 预取从 7–8 个降到 1 个，但没有消除上述交互 Long Task，且会改变详情导航预取行为，未保留。

### 7. 功能与视觉回归（合成环境）

- 390/1440 浅色、390 深色、390 reduced-motion：AwardWall 正常渲染 20 张卡；
- 坏图：mock 返回 404 时显示“奖状图片暂不可用”，20 个详情链接仍在；
- 字体：首页只预载 Inter；注入 `.font-mono` 后按需加载正常体 Mono；
- 键盘：Tab 可到达奖状链接，`focus-visible` 为真；**本轮改为 `ring-2 ring-inset`**，避免外层 `overflow-hidden` 裁切；实际 Tab 截图 `shots/183/390-focus-awardwall.png`，计算样式为 inset 2px box-shadow；
- 卡片详情 `href` 保持 `/awards/<id>`，未改路由。

## 未验证与限制

1. **无真实 API/预览环境**：本地 mock 不代表真实 TTFB、SQL/OSS、图片字节、认证/精选数据；没有配对 HTTP、Server-Timing 或 API #148 的真实基线。API #148 仍 open、0 评论，正文明确“仅修订方案与任务”；API #178（ETag/304）和 API #157（图片查询/资源）也未完成。
2. **不是真实 CWV**：headless Chrome + 模拟 CPU/网络 + 桌面机器，不能代表手机、Safari、微信或真实用户分位数；交错 A/B 的 20/20 只够描述 P95，P99 仍是样本极值，不能当稳定尾延迟。
3. **移动图片快照不完整**：700ms 时基线记录到 13/20 张、treatment 15/20 张；图片请求/字节/加载完成时间需由 #181/#64 补。
4. **20 张的 API 侧成本未配对验证**：API 源码显示 `resolvePublicAssetUrls` / `getPublicAssetVersion` 可能按赛事扫描，但本地 mock 没有真实 SQL/OSS；不能据此改服务端或声称首屏预算达标。
5. **管理台未真实运行**：只验证 CSS 仍含 `@font-face` 和按需加载；未登录管理台，不声称管理台视觉/布局回归正常。
6. **焦点已修但未做真机键盘回归**：已改为 `ring-2 ring-inset` 并用 Tab 截图验证；未在 Safari/真机做键盘走查。
7. **构建版本差异**：本地 Node 24.21.0 与 CI 22.23.3 不同；本地 `pnpm run build` 以 Node 24 执行并退出 0，仍不能替代 CI 的 Node 22 构建；远程 CI 结果推送后另记。
8. **Long Task 口径**：同构建交错 A/B 已把字体请求差异分离；但真实设备上的任务切分仍可能不同。资源限额来自 2026-10-21 部署文档，不是当前统一复核值；当前 API/Web SHA 也未配对。
9. **图片完成但动画透明**：本地快速滚动已看到图片 complete 而卡片 opacity 仍 0；这是需要另单复现的显示问题，本单未改动画。
10. **P95/P99**：字体交错 A/B 已扩到 20/20；跨构建/其它格仍 10/5 次。P95 只作描述，P99 未稳定估计；没有足够样本声称真实尾延迟。
