## 页面与消费要求

| 页面/交互 | 需求与接口边界 |
| --- | --- |
| /hall-of-fame | view=names，三个等级全部姓名/人数；轻量无照片长简介，不沿用首页20精选上限 |
| /hall-of-fame/[level] | 仅1/2/3，其余404；view=level&level=，全体成员及现役/荣誉和准确计数 |
| /profile/[id] | 沿旧userId URL，消费正式快照/当前获准照片/两个年份和履历，保留经验文章 |
| 管理邀请 | 姓名受限搜索→显示年级/学院/专业→明确选中userId并确认；改关键词清旧选择、取消/防乱序 |
| 管理编辑/进阶 | 邀请status、level、serving/honorary分离；expectedRevision冲突409保留输入，不自动覆盖；改级走milestones |
| 本人首次填报 | 姓名等快照确认、照片、主动公开同意必需；私有上传不等于提交，candidate未公开 |
| 本人换照 | active走photo-requests，pending仍旧公开图，可撤回再重提；不调用普通头像立即更新 |
| 后台照片申请 | 新旧图对比、授权私有preview、approve/reject；督导不审批，409后刷新真实状态 |

保留默认GET /api/hall-of-fame的原包裹、首页HallOfFameCompact、比赛showcase筛选、人物经验关联与旧隐私开关。不在Web读DB/私有服务，不使用危险HTML、不把私有key拼成URL、不返回内部审核资料。BFF新增路径/方法逐项登记，uploads继续现有专用转发；不放开admin通配写路径。

## 原稿执行补充与待确认项

1. 原稿的邀请请求示例缺少eventYear，但入选履历需要它。C0同时明确achievementYear与eventYear，A2邀请写入初始milestone；不把成绩年份当入选年份。
2. 等级名称/展示顺序/允许进阶方向由一处配置维护，原稿未确认正式称号与方向；可先用中性等级占位开发，正式政策由维护者确认，不从数字大小猜业务。
3. 普通成员PUT不得直接改level；入选/进阶操作事务写等级、履历、revision和审计。首次candidate→active由A4认领照片/同意校验，A5不能保留平行绕过入口。
4. 新照片scope从上传之初就必须有私有GET/HEAD控制，A3完成当前正式引用/版本校验，不等到最后审核UI才补。待审预览读取与审核写权限分别沿既有规则；督导不获得审批权，精确读取范围在C0核对冻结。
5. 照片申请后成员revision变化，审批不能静默拿新版本覆盖，返回409并按合同刷新重确认/重新申请。旧图在批准事务成功之前保留；不提前删除旧对象。
6. 原稿原有删除行为与新履历保护存在冲突，A5同时覆盖admin DELETE和本人撤回；未公开邀请可受控撤回，正式成员优先隐藏/归档，依法删除另走受控流程。
7. 新成员公开同意与旧隐私开关的优先关系、同意范围和撤销效果由C0明确；没有迁移授权的旧成员继续原隐私规则，不伪造授权时间。
8. 上传5MiB、320/960尺寸是方案建议值；服务端像素/频率/资源限额在A3结合现有预算确定并记录。不能用前端校验代替服务端资源控制。
9. 对旧邮箱/缺版本请求的兼容必须有字段边界与退役条件，不能用兼容分支绕过新首次发布或履历/照片约束。
10. R1生产执行以有权限维护者的批准窗口为前提；本次建单/文档不授权生产迁移、补录、删除或发布。应用回退保留新增数据，不为回退直接DROP履历/申请/审计。
